## 3. GUC wiring (Deliverable 2, backend)
One structural correction to the spec's mechanism: `get_current_user` **depends on** `get_db`, so the session is acquired *before* the user is known — an acquire-time `set_config` would always see NULL. I'll keep the ContextVar + `get_db` interface as spec'd but apply the GUC lazily and robustly:
- `ContextVar("current_user_id")` in `app/core/security.py`, set by `get_current_user` (and demo fallback) right after token verification — before any SQL runs, including the JIT user upsert (so the `users` INSERT passes RLS).
- A session `after_begin` event (Postgres dialect only; no-op on SQLite) runs `select set_config('app.user_id', :uid, false)` + `set_config('request.role', 'authenticated', false)` on each new transaction — session-scoped, survives mid-request commits, re-applied per transaction. Setting `request.role` is required so the app role can read the shared tables (spec's shared-read policy checks `request.role = 'authenticated'`).
- `get_db` finally: `select set_config('app.user_id', '', false)` reset on release (PG only).
- Unauthenticated requests → empty GUC → owner tables deny (correct).

## 4. RLS policy matrix (0003)
- **Owner-scoped** (`events`, `alerts`, `action_executions`, `enforcement_policies`, `audit_logs`, `media_files`, `incidents`, `response_executions`, `users`): split SELECT/INSERT/UPDATE/DELETE policies `owner_user_id = current_setting('app.user_id', true)::text` (`users` uses `id = ...`), with `WITH CHECK` on writes.
- **Shared read** (`response_catalog`, `organizations`): SELECT policy `current_setting('request.role', true) = 'authenticated'`; additionally an app-role policy so the backend can seed the catalog and (later) resolve orgs — documented deviation, otherwise `init_db` seeding and `/auth/me` break under RLS.
- **Child/join tables** (not in the spec's column list but RLS-enabled ⇒ deny-all without policies): `recommended_actions` / `incident_alerts` / `incident_events` get EXISTS-on-parent policies (owner via alert/incident); `organization_members` gets `user_id = current_setting('app.user_id')`. `response_executions` gets an `owner_user_id` column (addition to the spec's list — it's a first-class personal-workspace table; noted in DECISIONS.md).
